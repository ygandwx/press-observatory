# 技术与数据设计

## 架构决策

采用单仓库、模块化 Django 应用与独立采集进程。API 和 worker 共用模型、迁移及审核服务。API 尽快返回任务编号，网页通过查询任务状态显示进度。首版将业务表和任务表放入同一 PostgreSQL 实例，以事务关联任务、数据和执行记录。引入独立消息队列的依据是队列积压、数据库负载及并发需求的实测值。

| 部署单元 | 技术与职责 |
| --- | --- |
| Web | React + TypeScript + Vite + ECharts。浏览器状态保存页面偏好，筛选条件保存在 URL，可复制、刷新和返回。 |
| API | Django 5.2 LTS + Django REST Framework。响应同源请求，管理会话、权限、分页及审计。 |
| 数据库 | PostgreSQL。保存机构、文章、事件、审核、归档与任务状态；生产凭据由部署环境注入。 |
| Worker | Django 管理命令作为常驻进程。执行抓取、解析、AI 和生成草稿任务；超时与重试记录到对应任务。 |
| 调度与入口 | Ubuntu 主机通过 systemd timer 按北京时间投递周期任务；Docker Compose 管理 API、worker、DB 和同源 Web 入口。生产环境由反向代理终止 TLS。 |

M1 拟设目录为 `frontend/`、`backend/` 和 `deploy/`。后端按机构与信源、采集、事件与审核、统计与出版划分模块。具体小版本与依赖锁文件在 M1 初始化时确定。

## 数据边界与约束

| 实体 | 关键关系与约束 |
| --- | --- |
| 媒体机构、信源 | 机构有稳定 ID、别名、地区、层级、一级/二级分类及关注等级。机构可有多个渠道；跨机构的行业信源可独立存在。名册版本和来源随导入批次保存。 |
| 来源文章 | 每篇保留原始 URL、规范 URL、信源、标题、发布时间、抓取时间和核验状态。优先按信源稳定外部 ID 去重，否则用信源与规范 URL；正文指纹供复核。链接的来源渠道、文章发布者、事件主体分别存储。 |
| 行业事件 | 事件持有标题、摘要、发生日、分类、重要度、审核状态、首次批准时间。通过关联表连接多个机构和来源文章，一篇综合报道也可佐证多件事。关联对加唯一约束。 |
| 归并与审核 | 保留候选、被归并事件和来源历史。编辑可提出归并，审核人确认或拆回；服务在事务中检查版本、更新关联、写审计记录。列表聚合只计有效且符合条件的唯一事件 ID。 |
| 采集任务与执行 | 任务记录触发方式、信源、调度窗口、状态、尝试次数、租约期限及错误。定时任务的信源和窗口形成幂等键。每次尝试单独留痕。 |
| 日报、周报与签发版本 | 期次按报告类型和业务周期唯一；周报两个版本共用事件集合。草稿可改，签发保存版本、指标、原文引用、签发人和时间，更正产生新版本。 |
| 用户与审计 | Django 用户/组承载权限；审核、归并、签发、配置调整记录操作者、时间及变更摘要。自动批准使用独立系统身份和策略版本。 |

以北京时间表示业务日，时间戳用带时区类型存储。对审核状态、首次批准时间、事件与机构关联、任务状态和可领取时间建立查询索引。耗时查询以真实查询计划调优。

## 端到端运行

1. 调度器或编辑投递采集任务。worker 短事务领取到期任务并设置租约；联网和模型调用在事务外完成。进程退出后可重新领取过期租约，提交结果需匹配当前租约。
2. 采集器记录来源与发布时间，解析标题、摘要和正文证据。规范 URL 命中已有文章时更新抓取记录，保存必要的内容版本。部署方配置允许的信源、速率、响应大小和抓取超时。
3. 关键词和模型提出相关性、八类事件分类、摘要、依据及疑似重复项。保存模型标识、提示模板版本和引用。外部网页正文只作为分析材料；模型响应按固定字段校验。
4. 无关内容记录过滤原因；来源不明、链接失效、归并不确定或模型不可用时进入人工复核。只有来源已核验、符合策略且去重通过的事件可自动批准；首期默认人工放行，自动策略需经样本验收启用。
5. 批准服务事务内校验来源、设定首次批准时间和审计记录。统计卡和列表共享同一筛选对象。日报从已批准事件生成可编辑草稿，签发服务在同一事务中锁定版本和引用。
6. 失败记录可重试或转人工，带上执行阶段与错误类别。前端分别展示加载中、真实零条和加载失败，并提供重试。

## 接口草案

以下路径相对 `/api/v1`，作为 M1–M4 的接口设计起点。分页列表约定返回总数、结果和下一页。写请求由服务端检查权限与当前状态，重复请求复用结果或返回明确冲突。

| 行为 | 示例接口 | 关键约定 |
| --- | --- | --- |
| 浏览看板与事件 | `GET /dashboard`、`GET /events`、`GET /events/{id}` | 卡片返回数值、筛选条件和统计截止时刻；列表复用业务日期、时间字段、状态、分类和范围 |
| 浏览媒体档案 | `GET /media/{id}`、`GET /events?media_id=…` | 机构时间线与列表复用事件标识及可见范围 |
| 启动并跟踪采集 | `POST /collection-runs`、`GET /collection-runs/{id}` | 返回 202 和任务标识；按信源展示尝试、状态、错误和人工处置建议 |
| 审核与归并 | `POST /events/{id}/reviews`、`POST /event-merges` | 传目标状态、理由与预期版本；退回必须填原因；并发冲突返回 409 |
| 日报与签发 | `POST /reports`、`PATCH /reports/{id}`、`POST /reports/{id}/issues` | 创建或取回本期草稿，编辑要求版本匹配，签发权限单独校验；归档读取签发快照 |

## 部署与运行准备

开发、测试和生产分别使用独立数据库；配置仅提交样例。生产采集从经过配置的公共 HTTP(S) 信源读取，限制重定向目标和网络访问范围。抓取进程与数据库使用最小权限。备份包含数据库、版本及恢复所需配置说明，由部署方设置保留周期。M6 需记录恢复耗时、备份时间点、失败告警去向及回退结果。

技术参考见 [Django 5.2](https://docs.djangoproject.com/en/5.2/)、[Django REST Framework](https://www.django-rest-framework.org/)、[PostgreSQL 文档](https://www.postgresql.org/docs/) 和 [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)。
